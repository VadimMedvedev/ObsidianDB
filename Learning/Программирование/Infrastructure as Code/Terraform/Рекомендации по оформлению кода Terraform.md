
Есть определённые разработанные стандарты для написания кода terraform, чтобы сделать его масштабируемым и легко читаемым (ну и попросту красивым).

Основные моменты:
* Terraform уже включает в себя специальные инструменты форматирования кода, их можно запустить при помощи команд `terraform fmt` и `terraform validate`.
* Уже написаны линтеры для tf (см. TFLint).
* Для комментариев используется символ `#`.
* Использовать двойные ковычки.
* Разделять слова в названии переменных `_`.
* Определять тип и добавлять описание для каждой переменной.
* Добавлять опиание для каждого вывода.
* Незлоупотреблять `count` и `for_each`

### Форматирование кода

* Использовать два пробела в выступе для выделения вложенности блоков.
* Выравнивать знаки равенства в однострочных означиваниях переменных внутри одного блока.
* В каждом блоке в следующей последовательности, отделяемые между собой пустыми строками, идут следующие объявления:
	* Мета-аргументы
	* Обычные аргументы
	* Вложенные блоки
	* Мета-блоки
``` HCL
resource "aws_instance" "example" {
  # meta-argument first
  count = 2

  ami           = "abc123"
  instance_type = "t2.micro"

  network_interface {
    # ...
  }

  # meta-argument block last
  lifecycle {
    create_before_destroy = true
  }
}
```
* Все блоки должны быть отделены друг от друга пустой строкой (возможно кроме групп повторяющихся блоков).

Команда `terraform fmt` применяет все эти изменения к написанному коду. Для форматирования файлов не только в [[Инициализация рабочей директории|рабочей директории]], но и во всех неё вложенных, используем флаг `-recursive`.

Форматирование файлов можно настроить автоматически перед каждым комитом (https://git-scm.com/book/en/v2/Customizing-Git-Git-Hooks). 

### Валидация кода

Команда `terraform validate` проверяет синтаксическими методами код на ошибки. Это позволяет отсеит самые простые из них. Это также можно сдлеать хуком в git репозитории, или шагом в CI/CD pipeline.

### Название файлов

Рекомендации для названия файлов:
* `main.tf` файл содержащий все ресурсы и все источники данных.
* `outputs.tf` Хранит все блоки вывода в алфавитном порядке.
* `providers.tf` файл хранящий все объявления профайдеров
* `terraform.tf` файл содержащий один блок terraform.
* `variables.tf` файл со всеми переменными в алфавитном порядке
* `override.tf` файл, который хранит все переопределяемые определения. Такой файл, как и файлы оканчивающиеся на `_override.tf` будут загружаться последними. Желательно к оригинальным переменным добавлять комментарии, что они будут перепиываться в этих файлах.
* `network.tf`, `storage.tf`, `compute.tf` - подобные файлы объединяющие ресурсы по разным группам.

### Объявление ресурсов

Название ресурсов надо записывать в ковычках `"`. Каждое название должно быть уникальным.
Порядок объявления ресурсов не важен для terraform, но для читаемости, следует его выстраивать в логиченом порядке.

### Переменные

Перед тем как создавать любую переменную, стоит задуматься. Будет ли она вообще менятся от деплоя к деплою? Стоит ли её создавать?
Правила хорошего тона:
* Всегда задавать тип и описание переменной.
* Если переменная опциональна, то добавлять аргумент `default`.
* ИСпользовать параметр `sensitive` когда требуется.
* Добавлять, если требуется, блоки `validate`, но только если требуется.

Рекомендуемый порядок аругментов:
* Type
* Description
* Default
* Sensitive
* Validation blocks
